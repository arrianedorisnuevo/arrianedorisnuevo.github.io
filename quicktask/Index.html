// overview

A marketplace built around one honest constraint

QuickTask isn't trying to be instant delivery. It's built for tasks that can wait two days but shouldn't wait forever — the ones that quietly pile up on a busy person's list until they become a Saturday problem.

16services across 5 categories
48hminimum scheduling notice
3demo roles — customer, provider, admin
4payment methods, one modular layer
// problem

The task list that never gets shorter

Busy employees and founders accumulate a steady stream of small administrative, research, writing, and design work — cleaning up a spreadsheet, proofing a document, building a slide deck — that's too small to hire for and too tedious to get to. It sits there, unresourced, competing with everything else that matters more.

// solution

Describe it, schedule it, forget it

QuickTask lets someone pick a service, describe exactly what they need, choose a time at least 48 hours out, and pay upfront — then the task simply happens. No back-and-forth quoting, no chasing a freelancer for a status update. The 48-hour floor keeps the marketplace realistic: providers get enough lead time to do good work, not rushed work.

// design approach

Portfolio identity, SaaS product discipline

The case study you're reading borrows arriane.dev's dark, code-annotated voice — sequential labels, monospace data. The app itself deliberately steps away from that into its own product identity: warmer, calmer, built for someone doing a task, not reading a portfolio.

Why the app doesn't look like the portfolio

A marketplace someone might actually use needs to feel trustworthy and calm, not like a developer's showcase. Amber signals action and urgency without tipping into alarm; a mint accent is reserved for money and completion, so "paid" and "done" always read the same way.

Designing around the 48-hour rule

Rather than bury the constraint in fine print, it's surfaced everywhere a date gets picked — on the service page, in the request form, and again at the moment of payment — so no one pays for a slot that later gets rejected.

// technical approach

Architecture built to run on GitHub Pages, but not pretend to be a backend

The prototype is a static, client-rendered app so it can sit inside a GitHub Pages portfolio with zero build step. The data layer is written the way a real schema would be — with relationships and an auditable transaction ledger — so the leap to a real API is a matter of swapping the data layer, not re-architecting the UI.

Entities

Users, Provider Profiles, Services, Categories, Tasks, Payments, Wallets, Wallet Transactions, Messages, Reviews — each task links a customer, a provider, and a service, and carries its own status history rather than a single overwritten field.

Where a real backend would plug in

Scheduling validation, payment confirmation, and role-based access are all written as isolated functions with a comment marking the line where a real API call replaces the mock — PayPal and the crypto payment layer are built as swappable providers behind one interface, not hard-coded branches.

// challenges

What was actually hard about this

scheduling logic

Enforcing "48 hours from now," not "48 hours from midnight" — and re-validating it at payment time in case someone leaves the form open.

payment states

Modeling every branch a real payment can take — failed, refunded, disputed — as first-class statuses instead of a boolean "paid" flag.

marketplace roles

The same task looks different to a customer, a provider, and an admin — one data model, three permission-aware views.

wallet transactions

Treating Coins as a ledger of transactions rather than a single balance number, so every top-up, spend, and refund is traceable.

responsive design

Keeping Service → Request → Schedule → Payment fast on a phone, where the whole flow was actually designed first.
